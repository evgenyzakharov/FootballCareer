# Архитектура

Одно правило объясняет почти все решения ниже: **движок не знает ни про React, ни
про тексты, ни про случайность вне сида**. Состояние — обычный сериализуемый
объект, переходы — чистые функции, RNG восстанавливается из `(seed, метка, шаг)`.
Из этого следует, что карьеру можно переиграть один в один, положить в
localStorage, прогнать в тесте на десять полных карьер и отрендерить в двух
локалях без единой строки в коде движка.

## Слои

```
src/
  data/      клубы, лиги, страны, пулы фамилий — только данные, без логики
  engine/    вся механика: чистые функции над CareerState
  i18n/      ключ → { ru, en }; t() подставляет параметры
  ui/        React: читает состояние, вызывает переходы, ничего не считает
```

Зависимости идут строго вниз: `ui → engine → data`, `ui → i18n`.
`engine` **не импортирует** `i18n` и `ui`. Если движку нужен текст — он возвращает
не строку, а `Text = { key, params }`, и решение о языке принимается при рендере.

## Состояние

`CareerState` ([types.ts](src/engine/types.ts)) — единственный источник правды.
Ключевые поля:

| Поле | Зачем |
|---|---|
| `seed`, `step` | воспроизводимость: любой бросок = `Rng(seed, метка, step)` |
| `player` | возраст, 8 навыков, 8 показателей состояния, потенциал, черты, травмы |
| `contract` | клуб, срок, зарплата, аренда, задача на сезон |
| `season` | накопитель текущего сезона: статистика, роль, трофеи, множители шансов |
| `stage`, `queue`, `card`, `resolution` | машина сезона (ниже) |
| `history` | закрытые сезоны — это и есть таймлайн в интерфейсе |
| `relationships` | NPC и их отношение |
| `consequences` | отложенные последствия с возрастом срабатывания |
| `feed` | лента заголовков |
| `flags` | счётчики для связок между событиями и будущих ачивок |

Всё, что попадает в состояние, должно переживать `JSON.stringify` → `parse`.
Никаких классов, функций, `Date`, `Map` внутри состояния.

## Машина сезона

Сезон — шесть этапов в фиксированном порядке:

```
preseason → autumn → winter → spring → run_in → review
```

`enterStage` наполняет `queue` **битами**, а не готовыми карточками:

```ts
type Beat =
  | { t: 'event'; key: string; payload?: ... }  // конкретное событие
  | { t: 'random' }                              // выбрать событие в момент показа
  | { t: 'sim' }                                 // отыграть игровой блок
  | { t: 'season_end' }                          // трофеи, награды, развитие, возраст
  | { t: 'market' }                              // решение по клубу
```

Это центральное решение архитектуры. Карточка собирается в момент показа
(`openBeat`), поэтому она видит эффекты всех предыдущих решений этого этапа: если
на предсезонке вы поругались с тренером, следующая карточка уже строится с
упавшим доверием. Если бы биты разворачивались в карточки заранее, пришлось бы
пересобирать очередь после каждого выбора.

Что кладётся на каждом этапе:

| Этап | Биты |
|---|---|
| `preseason` | сменился тренер? → задача на сезон → 1–2 случайных события |
| `autumn` | первый вызов в сборную? → 1–2 события → бросок травмы → `sim` |
| `winter` | 1–2 события (трансферы, контракт, жизнь вне поля) |
| `spring` | событие → бросок травмы → `sim` |
| `run_in` | ключевой матч |
| `review` | турнир сборной? → `season_end` → `market` |

Плюс на любом этапе — сработавшие отложенные последствия (`dueConsequences`).

### Сезон без клуба

Клуба может не быть: игрок остался свободным агентом. Тогда `enterStage` уходит
в отдельную короткую ветку `freeAgentBeats` — почти все обычные ситуации требуют
клуба и без него читались бы бессмысленно.

```
preseason  free_agent_year — как прожить год
autumn     sim → отчёт без матчей
winter     trial_offer — зимний просмотр
spring     sim → отчёт без матчей
run_in     —
review     season_end → market
```

Такой сезон всё равно закрывается полностью: игрок стареет, навыки идут по
возрастной кривой (с множителем 0.2 — тренировок в одиночку мало), сезон
попадает в историю с `clubId: null`. Без этого закрытия возраст не увеличивался
бы и карьера зависла.

Как игрок туда попадает: дисквалификация за сдачу матча высушивает рынок
(`interest()` возвращает 0), выпадает `no_offers`, и там есть вариант остаться
без клуба. «Уйти дивизионом ниже» опирается на `fallbackOffers`, которые
игнорируют интерес клуба, — поэтому этот выход есть всегда и тупика не бывает.

### Насос

```
pump(state)   пока нет карточки и нет результата: достать бит → открыть его
choose(state, optionId)   разобрать выбор → применить эффекты → показать результат
ack(state)    закрыть результат → pump
```

`pump` имеет предохранитель на 64 итерации: если бит по какой-то причине не даёт
карточки (условие события перестало выполняться, предложений не нашлось), цикл не
зависает, а идёт дальше. Тест `career.test.ts` падает с `stuck: ...`, если насос
вернул состояние без карточки при незакрытой карьере, — это и есть страховка от
тихого зависания.

### Игровой блок

Сезон отыгрывается двумя блоками по 26 матчей (`BLOCK_MATCHES`). Один блок —
это `simulateBlock`: роль → доля минут → матчи → голы/передачи (Пуассон) →
оценка → сдвиги формы, свежести, доверия и трибун. Роль пересчитывается **после
каждого блока**, поэтому провал осенью реально стоит места в составе к весне.

Цепочка зависимостей, ради которой всё это существует:

```
доверие тренера → роль → минуты → статистика → оценка → доверие тренера
                                       ↓
                              рост навыков (по минутам)
```

## Эффекты

Событие не меняет состояние само. Оно возвращает **список эффектов** — данные, а
не действия:

```ts
{ t: 'gauge', key: 'coachTrust', delta: -14 }
{ t: 'injury', kind: 'acl', severity: 3 }
{ t: 'schedule', consequence: { eventKey: 'doping_shadow', inSeasons: 2, stage: 'autumn' } }
{ t: 'transfer', clubId: 'venezia', loan: false, wage: 240_000, years: 3 }
```

18 вариантов, все в `types.ts`, применяются в `applyEffect` в `career.ts`.
Такой формат даёт три вещи: эффекты тестируются без запуска события, интерфейс
может заранее показать, чем выбор грозит, и новый вид последствия добавляется в
одном месте.

Конструкторы-сокращения (`gauge`, `attr`, `money`, `injury`, `later`, `rel`, …)
лежат в [events/context.ts](src/engine/events/context.ts).

## События

78 определений: 55 участвуют в лотерее (`weight > 0`), 23 выдаются по сценарию
(`weight: 0` — структурные карточки, отложенные последствия, реакция на травму).
22 одноразовых за карьеру.

По каналам: жизнь вне поля 15, трансферы 12, медиа 11, тренировки 8, медицина 7,
клуб 7, раздевалка 6, сборная 6, матч 6. Актуальные счётчики — `npx tsx
scripts/counts.ts`.

Определение события — один объект:

```ts
{
  key: 'rival_signing',
  channel: 'locker',
  stages: ['preseason', 'winter'],   // где может выпасть
  once: false,                       // одноразовое за карьеру
  weight: 9,                         // вес в лотерее; 0 — только по сценарию
  when: (c) => c.club !== null && c.player.age >= 18,
  build: (c) => ({ bodyParams: {...}, options: [...] }),
  resolve: (c, id) => ({ outcome: 'won_place', effects: [...], headline: true }),
}
```

`build` и `resolve` вызываются **в разные моменты и с разным шагом RNG**. Отсюда
два правила:

1. Всё, что должно совпасть между карточкой и её разбором, считается
   детерминированно. Поэтому `wageFor` и `contractYears` — чистые функции от
   `(ovr, age, tier)`, а не броски.
2. Динамический выбор (какой именно клуб предложили) кодируется **в id опции**:
   `to:man-city`, `loan:venezia`, `switch:BRA`. `resolve` разбирает id и не
   зависит от того, что нагенерил `build`. Контекст, который в id не влезает,
   едет в `card.payload` (травма, турнир, список академий).

Ключ перевода для опции берётся по части id до двоеточия — `to:man-city` →
`ev.rival_offer.opt.to`.

## i18n

967 ключей, обе локали в одном файле рядом:

```ts
'ev.rival_signing.title': { ru: 'Конкурент на вашу позицию', en: 'A rival for your shirt' },
```

Расходиться им негде — они лежат в одной строке. Соглашение по ключам события:

```
ev.<key>.title            заголовок
ev.<key>.body             текст
ev.<key>.opt.<id>         подпись кнопки
ev.<key>.res.<outcome>    что вышло
ev.<key>.hl.<outcome>     строка в ленте новостей (если headline: true)
```

Подсказки на кнопках берутся из общего словаря `H` (~35 фраз вроде «риск травмы»,
«меньше минут») — они переиспользуются во всех событиях, поэтому словарь не растёт
пропорционально контенту.

`t()` подставляет параметры и умеет три типа значений: строку, число и
локализованный объект (`Club.name`, фамилия NPC) или вложенный `Text`
(`{ key: 'injury.acl' }`). Ключи с денежным смыслом (`wage`, `amount`, `fee`, …)
форматируются как деньги автоматически — по имени параметра, а не по типу.

Ненайденный ключ возвращает `⟨ключ⟩` и попадает в `missingKeys`. На этом стоит
тест: десять карьер рендерятся целиком в обеих локалях, и `missingKeys` должен
остаться пустым. Отдельной сверки словарей не нужно.

## Детерминизм

```ts
new Rng(state.seed, 'injury', state.step)
```

Генератор не хранит состояние в замыкании — он пересоздаётся из трёх значений.
`step` растёт на каждом бите и каждом выборе. Отсюда: одинаковый сид плюс
одинаковая последовательность выборов дают побайтово одинаковую карьеру (на это
есть тест), а сохранение в localStorage — это просто `JSON.stringify(state)`.

Цена: в движке нельзя использовать `Math.random()` и `Date.now()`. Метка RNG
должна быть уникальной для каждого места броска, иначе два разных решения на одном
шаге получат один и тот же результат.

## Сохранение

`save.ts`, ключ `football-career:state`, версия схемы в `STATE_VERSION`.

Загрузка проходит три шага: проверка формы (`looksLikeState` — битый или чужой
JSON не должен ронять игру), затем цепочка миграций, затем возврат состояния.
Миграции идут **по одному шагу версии**: ключ N в `MIGRATIONS` превращает
сохранение версии N в N+1. Пропускать версии нельзя — так каждая миграция знает
ровно одну форму на входе. Сохранение новее кода не принимается: откатывать
схему назад мы не умеем.

Подъём `STATE_VERSION` обязан сопровождаться миграцией. Тест `tests/save.test.ts`
проверяет и круговой обход, и подъём слепка v1, и отказ от версии из будущего.

Приватный режим и исчерпанная квота не ломают игру: хранилище оборачивается в
try/catch и игра продолжается без сохранения.

## Интерфейс

React 19, три колонки, без роутера и без стороннего состояния — всё состояние
игры живёт в одном `useState` в [App.tsx](src/App.tsx) и пишется в localStorage
эффектом.

```
career__left     Hud: OVR, клуб, контракт, задача, 8 показателей, навыки, черты
career__center   CardView / ResolutionView — карточка или результат выбора
career__right    Timeline (история сезонов) + Sidebar (люди, трофеи, лента)
```

Компоненты не считают игровую логику. Всё, что им нужно, приходит готовым из
`engine/career.ts` (`currentOvr`, `currentValue`, `careerTotals`) или прямо из
состояния. Локаль передаётся контекстом (`ui/locale.ts`), хук `useT()` — это
единственный способ получить строку.

## Инварианты

Их стоит держать в голове при правках:

1. `engine` не импортирует `i18n` и `ui`.
2. В движке нет `Math.random()` и `Date.now()`.
3. Всё в `CareerState` сериализуемо.
4. Функции движка не мутируют вход, а возвращают новое состояние.
5. Тексты в коде движка — только `Text`-ключи, никаких литералов.
6. Всё, что должно совпасть между `build` и `resolve`, считается детерминированно.
7. Новое событие обязано принести свои ключи в `i18n/content/events-*.ts`, иначе
   упадёт тест полноты локалей.

## Проверка

```bash
npm test                        18 тестов: карьеры, детерминизм, локали, сохранения, год без клуба
npm run lint && npm run build
npx tsx scripts/balance.ts 80   разброс по 80 карьерам со случайными выборами
npx tsx scripts/counts.ts       актуальные счётчики (события, ключи, клубы)
```

Интерфейс проверяется в headless-браузере: `scripts/dom-check.js` внедряется в
копию собранной страницы, щёлкает от интро до пенсии и складывает отчёт в
`<pre id="TESTOUT">` — количество карточек, увиденные этапы и каналы, найденные
`⟨ключи⟩` без перевода, ошибки консоли. Панель браузера на этой машине не
используется, поэтому проверка идёт по DOM, а не по скриншотам.
